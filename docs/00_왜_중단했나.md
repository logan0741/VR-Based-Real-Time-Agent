## 한 줄 결론

웹캠 2D 관절점에서 **SMPL-X 관절 회전(body_pose, 부모 기준 local axis-angle)** 을 뽑아낼 정답 라벨이 학습 데이터(013 피트니스자세)에 없었다. 그래서 MLP 가 내놓는 회전값은 학습이 잘 돼도(val_loss 0.08) 실제 추론에서 전신이 25~50° 기울었고, 3D 관절 좌표로 뼈를 직접 돌리는 우회로도 local/world 회전 불일치로 무너졌다. 같은 시점에 2D 뷰어는 119 FPS 로 정상 동작하고 있었으므로 프로젝트는 2D 관절점 앱(App 브랜치)으로 정리했다.

## 근본 원인

1. **정답 라벨 부재** — 013 피트니스자세 데이터는 3D 관절 좌표(24관절)만 있고 SMPL-X `body_pose` 가 없다. 좌표 → local axis-angle 을 계층적으로 근사했지만 근사치일 뿐이다.
2. **도메인 불일치** — 학습은 고정 카메라 5대, 추론은 다른 카메라(웹캠·전문가 시퀀스). 회전 루트(`global_orient`)가 가장 크게 흔들린다.
3. **표현 불일치** — SMPL-X 뼈 회전은 부모 기준 local 이다. 관절 좌표에서 곧바로 world 회전을 만들어 넣는 방식(방향 A)은 구조적으로 맞지 않는다.
4. **체크포인트 혼동** — 17×3→17×3 모델을 17×3→66 모델에 `strict=False` 로 로드한 배포 상태가 한동안 "포즈가 이상한" 원인이었다(실험 3).
5. **자원** — Unity 에디터 + SMPL-X 최적화 서버 동시 실행 시 시스템 메모리 93~98%.

어느 쪽이든 카메라 도메인 정규화(루트 회전 제거 또는 정면화)가 같이 필요하다.

## 대신 이긴 것 — 2D 관절점

실험 로그의 마지막 절 "2D 시스템 상태 (정상 작동)":

- 2D 뷰어(`http://localhost:8000/viewer/`) **119 FPS, 0.0ms latency**
- WebSocket 연결·실시간 스쿼트 인식·MediaPipe 클라이언트·전문가 포즈 2D 비교 정상

자세 교정에 필요한 것은 관절 각도와 반복 횟수였고, 이는 2D 관절점으로 이미 충분히 빠르고 안정적이었다. 그래서 최종 앱은 [`App`](../../../tree/App) 브랜치의 2D 관절점 방식으로 갔고, 3D 리프터 학습과 SMPL-X 피팅 자산은 [`Pose3D`](../../../tree/Pose3D) 브랜치에 남았다.
