# 지연 측정 — 방법과 결과

## 1. 무엇을 재나

질문은 하나다. **폰이 관절점을 보낸 순간부터 Quest 앱이 받을 때까지 서버·네트워크 구간이 얼마나 걸리나.** 그리고 그 시간 중 서버 처리(processed)가 차지하는 몫은 얼마인가.

## 2. 방법

도구: `final/latency_lab/measure_latency.py` (한 경로), `run_latency_suite.py` (로컬 + Cloudflare 연속), 실행 스크립트 `final/scripts/04_latency_check.ps1`.

1. 파이썬 프로세스 하나가 같은 WS 주소로 소켓 두 개를 연다. 하나는 **viewer 역할(보내는 쪽)**, 하나는 **app 역할(받기만)** 이다.
2. viewer 소켓이 `session_config`(`exercise_type: squat`, `sets: 1`, `reps_per_set: 8`)를 보내고 0.2 초 기다린다.
3. `final/latency_lab/data/sample_coco17_keypoints.json` 의 COCO-17 `[y, x, confidence]` 한 자세를 바탕으로, 팔·다리(11~16 번) 관절의 y 를 사인파로 ±0.025 움직인 **합성 프레임**을 만든다.
4. 90 프레임을 30fps 간격으로 `data_type: "keypoints"` 로 보낸다. 보내기 직전 `time.perf_counter()` 를 프레임 ID 별로 기록한다.
5. 두 소켓이 받는 메시지를 프레임 ID 로 맞춰 `받은 시각 − 보낸 시각` 을 잰다. 서버가 보내는 메시지는 두 종류다 — relay(`data_type: "pose"`)와 processed(`data_type: "feedback"`). 그래서 경로가 4 개다.
6. 마지막 프레임 후 3 초 더 받고 닫는다. 평균·중앙값·p90·p95·최대와 프레임 도착 수를 JSON·MD 로 쓴다.

같은 프로세스·같은 시계로 보내고 받으므로 시계 동기화 오차가 없다. 대신 Cloudflare 경로의 수치는 **측정 PC → Cloudflare → 서버 → Cloudflare → 측정 PC** 왕복 전체다. 2026-06-13 측정은 두 경로 모두 같은 Windows PC(Windows-10-10.0.26200, Python 3.8.10, 보고서 `metadata.platform`)에서 돌았다.

| 경로 이름 | 뜻 |
|---|---|
| viewer echo, live skeleton relay | 보낸 소켓이 자기 relay 방송을 다시 받기까지 |
| app receive, live skeleton relay | app 소켓이 relay 를 받기까지 → **앱 뼈대 지연** |
| viewer receive, processed feedback | 보낸 소켓이 처리 결과를 받기까지 |
| app receive, processed feedback | app 소켓이 처리 결과를 받기까지 → **앱 점수·피드백 지연** |

**재지 않는 것**: 카메라 권한·캡처, 브라우저 TF.js MoveNet 추론, 캔버스 그리기, Quest 화면 표시. 실제 체감 지연은 이 표보다 크다.

### 프레임 도착

두 측정 모두 relay·processed 가 viewer·app 양쪽에 **90/90** 도착했다. 서버가 처리 중에 들어온 프레임을 버리고 최신 것만 처리하는 구조라 processed 수가 보낸 수보다 적을 수 있는데, 이 측정에서는 버려진 프레임이 없었다.

## 4. 해석

1. **서버 처리는 병목이 아니다.** 로컬에서 앱 relay 평균 4.235 ms, processed 평균 9.509 ms — 전처리·횟수·DTW·피드백을 다 해도 relay 보다 평균 약 5 ms 더 걸린다.
2. **도메인 지연은 네트워크 몫이다.** Cloudflare relay 평균 201.012 ms 에서 로컬 relay 4.235 ms 를 빼면 약 197 ms 가 터널·인터넷 왕복이다. processed 와 relay 의 차이는 Cloudflare 에서도 약 4.7 ms 로 로컬과 비슷하다.
3. **relay 분리가 의미가 있었다.** 로컬 processed 의 p95(35.33 ms)는 relay p95(5.607 ms)의 6 배를 넘는다. 뼈대를 processed 에 묶었다면 이 꼬리 지연이 그대로 화면 끊김이 됐다.
4. **최대값 약 61~69 ms (로컬)** 는 relay·processed 가 같이 튀는 것으로 보아 서버 계산보다는 이벤트 루프·OS 스케줄링 순간 지연으로 보인다 — 프레임별 원인 분석은 하지 않았다.

`latency_suite_summary.md` 의 판독 규칙: 로컬은 낮고 Cloudflare 만 높으면 병목은 백엔드 밖이다. 둘 다 높으면 백엔드 전처리·큐·프레임 버리기를 본다.

## 5. 검증하지 못한 것

- **DTW 포함 여부.** processed 경로에 DTW 비용이 들어가려면 서버에 `dtaidistance` 가 있어야 한다. 보고서에는 서버의 설치 상태가 기록돼 있지 않다. 2026-10-12 에 작성자 PC 의 `.venv` 로 서버를 띄웠을 때는 `dtaidistance` 가 없어 DTW 가 꺼진 채 떴다. 6 월 측정 당시 DTW 가 켜져 있었는지는 확인할 수 없다.
- **실제 기기.** 폰 MoveNet 추론 시간, Quest 렌더링, 폰 ↔ Cloudflare 구간(측정 PC 가 아니라 폰에서 출발하는 경로)은 재지 않았다. [40_기록/user_work_plan.md](../40_기록/user_work_plan.md) 의 목표치(폰 1 대 end-to-end 150 ms 이하)와 비교할 수 있는 실측은 없다.
- **반복성.** 각 경로 1 회 측정이다.
