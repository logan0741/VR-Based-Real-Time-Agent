# 전체 흐름 — 단계별

폰 카메라 한 프레임이 Quest 화면의 뼈대·점수·피드백이 되기까지를 번호로 적는다. 원본은 [final/PIPELINE.md](../final/PIPELINE.md) 와 [40_기록/LAST_DANCE_PIPELINE_2026-06-09.md](40_기록/LAST_DANCE_PIPELINE_2026-06-09.md) 이고, 함수·상수 이름은 현재 코드에서 다시 확인했다.

```text
[폰 viewer]  1~5  ──keypoints (WS /ws/pose)──▶  [서버 relay] R1~R3 ──pose──────────▶ [Quest app] A1
                                                     │
                                                     └▶ [서버 processing] P1~P8 ──feedback──▶ [Quest app] A2~A7
                                                                                   └──────▶ [폰 viewer] (같은 방송)
```

서버는 연결된 모든 WebSocket 에 같은 메시지를 방송한다(`manager.broadcast_json`). 그래서 폰 viewer 도 relay·processed 메시지를 받는다.

---

## 0. 운동 선택이 먼저 흐른다 (앱 → 서버 → 폰)

1. 앱 첫 화면에서 운동·`세트 수`(기본 3)·`세트당 횟수`(기본 8)를 고른다.
2. 앱이 WS 로 `session_config` 를 보내고, `운동 시작` 을 누르면 `session_start` 를 보낸다. 둘 다 `exercise_type`, `sets`, `reps_per_set` 을 담는다.
3. 서버는 `session_control` 을 갱신하고(`expert_started_at_ms` 포함) 모든 연결에 방송한다.
4. 폰 viewer 는 이 방송과 1 초 간격 `/api/session-control` 폴링(`pollExpertExercise`)으로 선택 운동을 따라가고, `/api/expert?exercise=…` 로 전문가 관절점을 다시 받는다.
5. 앱과 viewer 는 서버가 주는 `expert_phase_ms` 로 전문가 포즈 재생 위치를 맞춘다.

## 1. viewer — 5 단계 (`final/s05_frontend/viewer.js`)

| # | 하는 일 | 코드 근거 |
|---|---|---|
| 1 | TF.js MoveNet **SinglePose Lightning** 을 불러오고 카메라를 연다. 폰 세로 화면이면 480×640 세로 제약을 먼저 요청한다 | `poseDetection.movenet.modelType.SINGLEPOSE_LIGHTNING`, `cameraConstraints()` |
| 2 | 비디오 프레임에서 포즈를 추정한다 (1.2 초 타임아웃·워치독) | `estimatePoses`, `DETECT_TIMEOUT_MS = 1200` |
| 3 | 픽셀 좌표를 `[kp.y / videoHeight, kp.x / videoWidth, score]` 로 정규화한다 | `payload = poses[0].keypoints.map(...)` |
| 4 | 내 뼈대를 서버 응답을 기다리지 않고 바로 그린다. 폰이 세로인데 스트림이 가로로 오면 **미리보기용 사본만** 회전한다 | `correctMobilePortraitPayload` → `drawSkeleton("user-canvas", displayPayload, …)` |
| 5 | 원본 `payload` 를 `{data_type:"keypoints", frame_id:"cam_N", client_timestamp_ms, payload}` 로 약 15fps 보낸다 | `SEND_INTERVAL_MS = 66` |

1~5 는 WebSocket 이 열려 있을 때만 돈다(`canSend`). 카메라는 `localhost` 가 아니면 HTTPS 에서만 열린다.

## 2. 서버 relay — 3 단계 (`final/s02_backend/server.py`, `websocket_endpoint`)

| # | 하는 일 |
|---|---|
| R1 | `data_type: "keypoints"` 를 받자마자 `data_type: "pose"`, `keypoints_2d` 로 모든 연결에 방송한다 |
| R2 | `debug` 에 `relay_only: true`, `client_timestamp_ms`, `server_received_ms`, `server_relay_sent_ms` 를 붙인다 |
| R3 | 그 프레임을 `latest_keypoints_msg` 에 덮어쓴다. 처리 작업이 돌고 있지 않을 때만 새로 띄우므로, 처리 중에 들어온 프레임은 최신 하나만 남고 나머지는 버려진다 |

이 경로가 앱의 "내 자세" 를 움직인다. 무거운 계산은 여기 끼지 않는다.

## 3. 서버 processing — 8 단계

`process_latest_keypoints` 가 최신 프레임을 스레드 풀(`run_in_executor`)에서 `FastPosePipeline.process_keypoints` → `_process_2d_only` → `PreprocessingSession.process` 로 넘긴다. 운동이 바뀌었으면 먼저 그 운동의 전처리 세션을 새로 만든다(`sync_session_control`).

| # | 단계 | 코드 | 핵심 값 |
|---|---|---|---|
| P1 | 카메라 가시성 게이트 | `_camera_visibility_message` | 운동별 `keypoints_used` 의 confidence ≥ `0.12`, 좌표가 `0.01 ~ 0.99` 안. 실패하면 안내 문장 + `countable=false` 로 즉시 반환 |
| P2 | 자세 정규화 | `PoseNormalizer` | 엉덩이 기준 원점 이동, 어깨–엉덩이 거리로 크기 정규화, 최근 `norm_buffer_size`(7) 프레임 평활 |
| P3 | 횟수 감지 | `RepDetector` (`rep_rules.py`, `rep_signals.py`) | 각도 상태 머신. [02_횟수_규칙](20_판정_규칙/02_횟수_규칙.md) |
| P4 | DTW·점수 | `DTWComparator`, `ScoreEngine` | `dtw_interval`(3) 프레임마다 최근 `n_frames` 창과 전문가 시퀀스 비교. `dtaidistance` 가 없으면 건너뛰고 점수 기본값 50 |
| P5 | 피드백 엔진 | `FeedbackEngine.analyze` | `FEEDBACK_INTERVAL_FRAMES`(8) 프레임마다, 또는 새 rep 이 끝났을 때만 돈다. 그 사이엔 직전 결과 재사용 |
| P6 | 피드백 hold | `FeedbackPolicy.consider` | 새 피드백을 받으면 `target_fps × 3` 프레임 유지, 그동안 `feedback_event=false` |
| P7 | 빨간 관절 | `bad_joints` | 피드백 엔진의 관절. 피드백이 `측정 중` 상태면 `PostureAnalyzer` 피로도 요약(`양호`·`보통: …`·`주의: …`)과 그 근육의 관절로 대체 |
| P8 | 세션 진행 | `manager.attach_progress` → `session_progress.exercise_progress` | `total_target_reps = sets × reps_per_set`, `current_set`, `rep_in_set`, `completed` |

결과는 `data_type: "feedback"` 로 방송된다. `countable=true` 인 프레임만 세션 기록(`session_tracker.record_frame`)에 들어간다.

## 4. app — 7 단계 (`final/src/`)

| # | 하는 일 | 코드 |
|---|---|---|
| A1 | relay `pose` 프레임으로 내 2D 뼈대를 갱신한다 | `useWebSocket.ts`, `SkeletonCanvas2D.tsx` |
| A2 | processed 프레임으로 점수·횟수·세트·피드백·빨간 관절을 갱신한다. `countable=false` 면 문장만 보여주고 점수·횟수·샘플에 넣지 않는다 | `App.tsx` |
| A3 | 운동 선택 시 `session_config` 에 `exercise_type`, `sets`, `reps_per_set` 을 실어 보낸다 | `App.tsx` → `selectExercise` |
| A4 | 서버가 session control 을 방송해 폰 viewer 가 같은 전문가 포즈를 불러온다 | 0 절 참고 |
| A5 | 서버가 `total_target_reps` 를 계산한다. 앱은 서버 progress 를 그대로 표시한다 | `session_progress.py`, `workoutProgress.ts`(서버 값이 없을 때만 쓰는 fallback) |
| A6 | `completed=true` 가 오면 수동 `운동 종료` 와 같은 `handleEndSession` 을 자동 실행한다 | `App.tsx` |
| A7 | 결과 화면에 결정적 최종 리포트를 그리고 `/api/tts/final-feedback` 로 음성을 요청해 재생한다 | `buildFinalFeedback`, `ResultPanel.tsx`, `final/s07_tts/` |

`feedback_event=true` 인 피드백만 운동 중 로그와 최종 분석 샘플에 쌓인다.

## 5. 지연 측정이 보는 구간

`final/latency_lab/` 는 브라우저 대신 파이썬 프로세스 하나가 viewer 역할 소켓과 app 역할 소켓을 함께 열고, 합성 COCO-17 프레임을 보내 다음 네 구간을 잰다.

| 측정 경로 | 위 단계로 보면 |
|---|---|
| viewer echo, relay | 5 → R1 → (보낸 소켓이 다시 받음) |
| app receive, relay | 5 → R1 → A1 |
| viewer receive, processed | 5 → R3 → P1~P8 → (보낸 소켓) |
| app receive, processed | 5 → R3 → P1~P8 → A2 |

카메라 권한, MoveNet 추론(1~3), 캔버스 그리기(4, A1)는 들어가지 않는다. 방법과 수치는 [30_지연_측정/01_측정_방법과_결과.md](30_지연_측정/01_측정_방법과_결과.md).
